## 起因：想从仓库历史中彻底删掉一个文件

项目里有个叫 `test.cocojson` 的文件，当初顺手提交了上去，后来发现它其实不应该出现在仓库里。普通 `git rm` 只能删掉当前版本，历史记录里还会一直带着，于是想到了 `git filter-repo`——Git 官方现在推荐的历史重写工具。

在这之前，我用 pip 安装了它（没错，就是那会儿随手装的 `git-filter-repo`，后来差点没想起来叫啥）：

```bash
pip install git-filter-repo
```

然后进入仓库，执行了这么一条命令：

```bash
git filter-repo --path test.cocojson --invert-paths --force
```

- `--path test.cocojson`：指定要操作的文件
- `--invert-paths`：反转匹配，**删除**这个文件，保留其他所有内容
- `--force`：强制执行（因为仓库不是刚刚克隆的）

命令很快就跑完了，输出显示解析了 11 个提交，新历史写入成功，还提示我已自动删除了 `origin` 远程（这是 filter-repo 的保护机制，防止误推）。接着我把 `origin` 重新添加回去，强制推送到了远程仓库。

## 诡异的现象：同一个提交里的其他文件“消失”了？

推送完之后我检查了一下，突然发现——原本和 `test.cocojson` 同一个提交里的其他文件好像也凭空蒸发了。我开始怀疑是不是命令写错了，是不是 `--invert-paths` 没生效，或者工具把整个提交删掉了。

反复查看本地仓库的 `git log`，历史看起来确实乱七八糟，提交之间的关系也特别古怪，我差点就要认为 `git filter-repo` 有 bug，或者自己的操作毁掉了整个项目。

## 真相：只是我自己忘了重新克隆

后来冷静下来想到，`git filter-repo` 重写的是整个提交历史，所有 commit 的哈希值都变了，但我本地仓库的远程追踪引用、reflog、以及可能残留的某些缓存还指向旧的对象。再加上我强制推送后没有重新 fetch，本地仓库处于一种“半新半旧”的分裂状态，所以看到的文件关系自然就不准确了。

我试着做了一件很简单的事——从远程重新克隆了一份干净的仓库：

```bash
git clone https://github.com/ImLeonLi/SymPointV2.git fresh-clone
cd fresh-clone
```

打开一看，历史记录清晰了，`test.cocojson` 彻底消失，同一个提交里的其他文件完好无损。原来那一切混乱，都是因为我继续在使用已经被重写过的“脏”本地仓库。

## 血泪教训：重写历史前一定要备份

这件事让我深刻认识到几个必须遵守的原则，尤其是对于那些打算重写并推送公共仓库历史的人。

### 1. 操作前，千万做好完整备份

最简单的备份方式就是**在另一个目录里克隆一份完整的仓库**：

```bash
git clone /path/to/original/repo /path/to/backup
```

或者，如果你想让备份更轻量且完整保留所有分支、标签和引用，可以用 `--mirror`：

```bash
git clone --mirror /path/to/original/repo /path/to/backup.git
```

这样生成的 `backup.git` 是一个裸仓库，可以通过 `git clone backup.git` 随时完整恢复。还有一种同样有效的方法：直接复制整个项目文件夹（包括隐藏的 `.git` 目录）到另一个位置，但注意复制时不要使用任何会忽略隐藏文件的工具。

**千万不要**依赖 `git reflog` 或本地残留对象来“亡羊补牢”——`git filter-repo` 默认会清理掉旧对象，那些救命稻草可能早被扔掉了。

### 2. 推送到远程后，这一改变就是永久的

一旦你执行了 `git push --force`（甚至某些情况下的普通推送），远程仓库的历史就已经被重写了，所有协作者的本地仓库都会与新的历史产生冲突。**这种改变是不可逆的**（除非你还有远程之外的备份）。这也是为什么 `git filter-repo` 会主动删掉你的 `origin`，它想让你想清楚再推。

### 3. 推送后，所有人必须重新克隆，而不是 pull

这一点怎么强调都不为过。**重写历史并推送之后，本地那套被重写的仓库就不要再用了。** 你应该（并且也必须）重新从远程克隆一份干净的副本：

```bash
git clone <remote-url> new-local-repo
```

旧的本地仓库里充斥着过时的对象、错乱的引用，看似能工作，但随时可能在 `log`、`diff`、`merge` 时给你一堆难以理解的结果。所有参与这个仓库的协作者也都要做同样的事：删掉旧本地副本，重新克隆。

## 小结

`git filter-repo` 是个非常高效、精准的工具，但它操作的是整个 Git 历史，威力巨大。这次“文件消失”的虚惊一场，问题不在工具，而在于我忽略了操作后的环境清理。备份、确认、再推送，推送后重新克隆——这“三步走”应该成为每次历史重写的肌肉记忆。

希望这篇文字能让你在用 Git 改写历史时少踩一个坑，毕竟有些历史，还是早点看清楚比较好。
